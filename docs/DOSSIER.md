# KinRin — session dossier

What the session established, and what the plan deliberately no longer contains.

`PLAN.md` carries the instructions plus the reasoning needed to act on them. This file carries
the full rationale, the history and the dead ends. If a decision in the plan looks arbitrary,
the reason is in this file.

Session date: 27 September 2026. Measured target: Fedora 44.

## 1. Decisions and their reasoning

The plan carries each decision with the reasoning needed to act on it. This table is the rest of
the why: what the decision rules out, and what would have gone wrong without it.

| Decision | Reasoning |
|---|---|
| Base on `:latest`, no pin | A pin goes stale silently in an image published monthly. A pin that breaks is a false incident; a stale pin is invisible. |
| RPM, not Flatpak | Everything Steam needs is already in the Fedora repos. Flatpak would have forced a `flatpak override --talk-name=org.freedesktop.Flatpak` for host access, for no gain. |
| Steam and Discord from RPM Fusion `nonfree` | Neither has an upstream `.src.rpm`: a COPR cannot rebuild them. RPM Fusion is the only sane non-Flathub route. It is proprietary content, accepted knowingly. |
| No gamescope | Two distinct roles, both out of scope: session compositor (living-room hardware) and per-game wrapper (must be enabled by hand in each game, so half the games would ignore it). |
| No group for `greeter` | DRM access is not a group, and the two node types come from **different** rules: `card*` through the logind ACL (`70-uaccess.rules:46`), `renderD*` world-accessibly through `50-udev-default.rules:61` (`MODE="0666"`) — so do not assume one rule covers both. `input` also grants reading `/dev/input/event*` — capturing keystrokes at kernel level, for the process drawing the login screen. |
| VRR over IPC, not a file | `niri msg output <NAME> vrr on --on-demand` — read the real name with `niri msg outputs`, `<NAME>` is a placeholder — touches no file, so it survives `dms setup` by construction (PLAN.md §4.4). The config-file route lands in `dms/outputs.kdl`, which quickshell rewrites. |
| `dms` bound to niri by a `Wants=` drop-in, **plus `PartOf=` the other way** | `systemctl --user enable dms` starts DMS in **every** session, so a drop-in is required. But `Wants=` has **no stop semantics at all** (`systemd.unit(5)`): it starts `dms.service` and does nothing more. Without `PartOf=niri.service` in a `dms.service` drop-in, DMS outlives the compositor and criterion 2d's "not at all under Plasma" guarantee is void. `dms.service` already carries `PartOf=graphical-session.target` (`assets/systemd/dms.service:3`), so the session ending stops the unit anyway — the drop-in makes the stop *with niri* unconditional: belt-and-braces, not the only stop path. Two files, two jobs. |
| The `local.kdl` anchor is `../local.kdl`, and it is prepended | An include resolves against the directory of the file that includes it, and `binds.kdl` sits in `dms/` — so a bare `local.kdl` would fail loudly, pointing at `~/.config/niri/dms/local.kdl`, a file nothing writes. `optional=true` is what makes a wrong path fail silently instead — the loud failure belongs to the bare form alone, so the path is a review obligation rather than a build gate. It is also **prepended**, never appended: niri accepts `include` only at the top level, and inside another node it is a parse error. This is the defect I introduced while fixing an earlier one. |
| greetd config uses 0.10 syntax | Fedora 44 ships greetd ≥ 0.10, which takes `[default_session] command = "dms-greeter"` — a command line, not a path. The 0.8 form `default_session = "dms-greeter.desktop"` is a table in 0.10 and the greeter never starts. greetd never looks in `/usr/share/wayland-sessions/` at all. |
| One signing model, not two | Earlier drafts said the private key never leaves the image *and* that CI signs with it. Both cannot hold. The model is now: the `signing` module contributes the **verification policy** the image ships, the private key **never enters the image** (CI secret), and the signature over the pushed digest is produced at publish. The **public** key is published and is what the verification uses. This is a statement of the model, not a verified reading of the module — PLAN.md §6.1 asks for the policy to be inspected in the built image and refuses to claim the image verifies if that inspection prints nothing. |
| Eight module files, four of them `script@v2` | `flatpak.yaml`, `niri-config.yaml`, `theme.yaml` and `orca.yaml` are `type: script@v2`: the first two are multi-command shell steps in one layer, and the last two **fetch a URL**, which no official BlueBuild module does — `files` writes paths from the repo and has no way to download or to execute. `theme.yaml` also runs the `jq` shape assertion. The other four (`dnf`, `files`, `systemd` for the system units, `os-release`) are official types. |
| `DankMaterialShell` and `danksearch` are already in Fedora, and none of the three COPR names are | `dnf repoquery` re-read 2026-09-30 returns `DankMaterialShell-1.4.4` and nothing for `dms`, `dms-cli` or `dms-greeter`, so the three COPR names are still all needed; the version itself will move with the repository, so what is established is the landing, not the number. So the COPR still earns its place, and the §9 monitor must match on the COPR package names — a trigger of "DMS arrived" is already true and would break the build. `danksearch` is left out of this row on purpose: a §2 row records that **Fedora 44 offers it too**, and which of the two candidates won was not recorded, so "it is in Fedora" is not the operative fact. |
| `niri` already requires `xwayland-satellite` | Verified: `niri-26.04` carries it as a hard `Requires: >= 0.7`. The declaration stays as insurance against a future niri relaxing it, but the reason recorded for it was wrong. |
| Plasma fallback kept, not stripped | A niri-only image cannot be logged into after any niri regression. `plasma-workspace` and `kwin` stay installed, which lets the greeter offer Plasma next to niri — whether it does is criterion 13. Either way PLAN.md §1 guarantees the `Ctrl+Alt+F3` then `startplasma-wayland` path, and criterion 6 confirms the session file and the command resolve. |
| The three environment variables in **three** drop-ins, and the `dms.service` one carries all three | `/etc/environment.d/` is global, so it would hand the gtk3 platform theme to the Plasma fallback too. They go in **three** files, because systemd does not pass one unit's `Environment=` to a unit that it merely `Wants=` — a drop-in on `niri.service` alone would never reach DMS, nor anything DMS launches. PLAN.md §4.7. |
| extest not shipped, procedure kept in §4.9 | Not a session-wide preload: PLAN.md §4.9 scopes it to `/usr/bin/steam` alone, by cloning the shipped `/usr/share/applications/steam.desktop` into `/usr/local/share/applications/` with `install -D` and rewriting only its `Exec` to `env LD_PRELOAD=/usr/local/lib64/extest/libextest.so /usr/bin/steam %U` — never a hand-written stub, so it would reach Steam and nothing else. `/usr/local/share/applications` because that directory precedes `/usr/share/applications` in `$XDG_DATA_DIRS`, and `/usr/share/applications` is where the `steam` RPM actually ships its launcher. `/usr/local/lib64/`, because a 32-bit object cannot be preloaded into the 64-bit `steam` the RPM ships, and an **overlay** because `mask` is systemd vocabulary for `/dev/null` and a file shipped by a package reverts on update. It is a third-party binary from a named fork, `nmd2k/extest-steam-input-fix`, and the whole thing is conditional on criterion 22: a Steam crash on gamepad connect is unverified here, so the image ships no remedy for a fault it cannot show. That remedy is a **host-side** workaround, not image content: on Atomic `/usr/local` is a symlink to `/var/usrlocal`, so it is machine state under `/var` — the persistence §3.2 relies on — and **nothing needs redoing after a `bootc switch`**. A library under `/usr/lib64` is what a switch would wipe, and `/usr` is read-only on a booted host without `bootc usroverlay`. |
| No Flatpak applications preinstalled, no remote enabled | The `flatpak` package stays; no application is installed and no remote is active. A recipe step is still needed, and it is now six commands in a `script@v2` module's `snippets:` — there is no recipe `postprocess` key. The `%post` only *enables* `flatpak-add-fedora-repos.service`, and a unit enabled during a container build does not run, so "the `%post` already added a remote" is an **assumption, not an observation** (PLAN.md §3.2 says the same). The commands: `install -d /var/lib/flatpak` (absent from the base), then `remote-delete --system` for **both** `fedora` and `fedora-testing` (the unit has two `ExecStart` lines), then the empty marker, then the `/dev/null` mask symlink `ln -sf /dev/null /etc/systemd/system/flatpak-add-fedora-repos.service` — the mask, not the marker, is what survives the `bootc switch` path, because bootc treats `/var` in the image like a Docker `VOLUME`. The symlink is written by hand rather than through `systemctl mask` (PLAN.md §3.2), and it targets `/etc/systemd/system`, which is what `systemctl mask` writes. |
| `dms-cli` vs `danksearch` and `matugen` | `dms-cli` is a hard `Requires:` of `dms`, guaranteed. `danksearch` and `matugen` are only `Recommends:` (`distro/fedora/dms.spec:27,28`) — absent if the build disables weak dependencies. `danksearch` costs the greeter its search; `matugen` costs the whole of §4.12, silently. |
| opencode not shipped | The `curl \| bash` script installs into the home, so it is outside the image and untouched by `bootc upgrade`. The user runs it once. |
| orca from its GitHub RPM | It is the only one of the two tools that fits immutability: `dnf install`, lives in the image, follows `bootc upgrade`. The module takes `releases/latest`, which is not a pin. |
| Theming scope cut to DMS + matugen | matugen rewrites colours only and leaves widget style, icons and cursor alone, so Breeze stays underneath and covers whatever the colour scheme misses. That *is* the "Dracula over Breeze" fallback the user asked for, and it is the mechanism's natural behaviour. The dracula repository has no chaining of any kind — no `Inherits=`, no parent declaration. |

Breeze consequently does not apply to Dolphin, Konsole or Kate under niri — it applies to the Plasma fallback, where matugen repaints the colours on top. |

| `config.kdl` seeded into the skel, not only `/etc/niri/` | An include resolves relative to the directory of the including file. Without a user-side `config.kdl`, `/etc/niri/config.kdl` reaches `/etc/niri/dms/colors.kdl` and never sees what matugen writes. |

The one thing the registry copy does **not** carry is a licence: the source repository declares none for this file, so it cannot be filed under dracula's MIT and PLAN.md §10 has to carry it as an unlicensed component on its own line |

So the theme will not appear there. It will appear in **Settings → Theme**, which scans `~/.config/DankMaterialShell/themes/` directly with no network. Faking the browser needs a local git registry and `Pull` against it, which is unverified. Not worth it. |

| `/usr/share/dms/cli-policy.json` is written by `files.yaml` | `dms` refuses to touch an immutable system: `dms setup headless` carries `PersistentPreRunE: requireMutableSystemCommand` (`core/cmd/dms/commands_setup_headless.go:15`, gate at `core/cmd/dms/immutable_policy.go:252`) and plain `dms setup` the privileged variant (`commands_setup.go:24`). The gate reads `/usr/share/dms/cli-policy.json` then `/etc/dms/cli-policy.json` (`immutable_policy.go:17-18`) and fires when the system reads immutable **and** the command matches `blocked_commands` — and this base reads immutable twice over, `/run/ostree-booted` first (`:167`) and `VARIANT_ID` read at `:178` and tested against the marker list at `:197` (the return is `:198-199`), which it satisfies with `kinoite`. ## 5. Dead ends

Recorded so they are not repeated.

- **Queryable Xwayland in a container**: six attempts, six failures. Headless Weston starts,
  Xwayland starts and writes its log, but **no listening socket is ever opened** — both
  `-listen tcp -port` and `-listenfd` with a fifo failed. `xdpyinfo` (a harness failure, first read as a result) never connected.
  Criterion 22 cannot be simulated this way.
- **`dnf provides '*/Xwayland'`**: the grep `^[a-z0-9][a-z0-9.-]*` excludes uppercase and returns
  `xorg-x11-server-`. The package is spelled with a capital **X**.
- **`dnf download --resolve`** pulls 400 packages and `head -1` takes the first alphabetically,
  not the right RPM.
- **`xorg-x11-utils` does not exist in Fedora**: the umbrella package is gone, and each tool
  is its own package — `xdpyinfo` is a separate one. A single unmatched argument **aborts the
  entire dnf transaction**, so nothing installs until the name is right, and without that the
  missing package is easy to miss. Excluding it with `-x xorg-x11-utils` drops the request
  without delivering the tool, which is why the six attempts above never got an `xdpyinfo` to
  connect.
- **`Xwayland 99 -rootless`**: no positional display number. It needs `-listenfd` or
  `-listen tcp`.
- **`podman run` without `-i`**: stdin closes immediately, the script never runs, and the output
  contains nothing but the image pull.
- Concluding a `.so` from source code rather than `readelf -d` caused an unnecessary
  `libwayland-client.i686` to be pulled in.
